Common Cryptographic Mistakes

Rolling Your Own Crypto

Designing a custom, homemade encryption scheme instead of using established, publicly vetted algorithms is a classic mistake — even skilled engineers frequently introduce subtle flaws that professional cryptographers, having studied established algorithms for years, would catch. Established, widely-reviewed algorithms exist precisely because cryptography is unusually easy to get wrong in ways that are not obvious.

Key Point. "Don't roll your own crypto" is one of the most consistently repeated pieces of advice in security — use established, standard algorithms and libraries instead of inventing new ones.

Outdated Algorithms

MD5 and SHA-1 were once standard hashing algorithms but are now considered broken for security purposes (attackers can deliberately create different inputs producing the same hash — a "collision"). Continuing to use them for security-relevant purposes (not casual, non-security checksums) is a real, avoidable risk.

Hardcoded Keys

Embedding an encryption key directly into application source code means anyone who can read that code (including through a leaked repository, or basic reverse-engineering of a compiled app) can extract the key. Keys should be stored and loaded separately from the code itself, ideally in a dedicated, access-controlled secrets management system.

Protecting Data in Every State

Data can exist encrypted at rest (in a database) but unencrypted in other states — sitting in server memory, appearing in application logs, or included unencrypted in a backup. A complete approach considers protection across every state data actually exists in, not just the most obvious one.
