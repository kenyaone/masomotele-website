Authentication and Session Security

Session Tokens

After a successful login, a website typically issues a session token (often stored in a cookie) that proves "this browser is the logged-in user" for subsequent requests, without requiring the password to be resent every time.

Session Hijacking

Session hijacking occurs when an attacker obtains a valid session token — through XSS stealing a cookie, network interception, or a predictable/guessable token — and uses it to impersonate the legitimate logged-in user without ever needing their actual password.

Key Point. A stolen session token can be just as dangerous as a stolen password — it grants the same active access without needing to know any credentials at all.

Secure Cookie Flags

The Secure flag ensures a cookie is only ever sent over encrypted HTTPS connections, never plain HTTP. The HttpOnly flag prevents JavaScript from directly reading the cookie's value — meaningfully reducing the impact of an XSS flaw, since even injected script cannot steal an HttpOnly session cookie.

Session Timeout and Re-Authentication

Sessions should expire after a period of inactivity, limiting how long a stolen or abandoned session remains usable. For especially sensitive actions (like a large money transfer on SafariPay), requiring re-authentication even within an active session adds an extra check at the moment it matters most.
