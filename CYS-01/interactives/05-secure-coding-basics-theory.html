Module 5 · Lesson 5.5

Secure Coding Basics

Client-Side Validation Is Not Security

JavaScript running in a customer's browser can check that a form field looks correct before submitting — but an attacker can bypass the browser entirely and send crafted requests directly to the server. Client-side validation improves user experience; it provides zero actual security on its own.

Key Point. Any validation that matters for security must be enforced on the server — the browser and its JavaScript are entirely under the attacker's control, not to be trusted.

Server-Side Validation and Sanitisation

Every piece of input reaching the server — regardless of what client-side checks supposedly already happened — should be validated and sanitised there too, since the server has no way of knowing whether a request actually came through the real, unmodified client application.

Failing Securely

When something goes wrong (an error, an exception, an unexpected condition), a system should fail securely — defaulting to denying access or hiding sensitive details, rather than accidentally granting access or leaking internal information in an error message.

Shift Left

"Shift left" means considering security throughout development — in design, coding, and testing — rather than only at the very end (or worse, only after an incident). Fixing a design-level security flaw late in development, or after launch, is far more costly than addressing it early.
